# Master Agent System

Project-neutral Codex skill pack for coordinating long-running, multi-agent project work through a non-implementing Master Agent control plane.

The system is designed to keep project continuity outside chat history by using structured ledgers, packets, heartbeats, role contracts, root authorization envelopes, material behavior-domain checks, guard-obligation packets, optional round-log snapshot evidence, repair-execution-log document memory, token budgets, runtime supervision, review gates, and a governed correction-learning layer.

## Experimental Independent Module Runtime

The opt-in `master_agent_runtime` package starts the v2.1 architecture: one persistent native root session per module owner, a persistent Master, transactional dispatch and inboxes, immutable submissions, independent validation, and automatic Master review/rework/integration. Each owner handles its full engineering lifecycle. The legacy skill/CLI below remains available separately; this package does not activate it.

Use Python 3.11+ (tested with 3.12 and 3.14) from this repository. A single JSON strategy handoff supplies `root`, `objective`, `modules`, `token_budget`, and `integration_validation`. Each module supplies `key`, `objective`, `paths`, optional `dependencies`, and `validation`. Validation steps use structured `argv` and optional `timeout_seconds`; `{candidate}` and `{context}` expand to readonly artifact/source paths. The initial handoff requires the module list and independent acceptance checks; automatic Strategy-to-Master module derivation is still pending. IDs, native bindings, corrections and review messages are generated by the host.

```bash
python3.12 -m master_agent_runtime --state /absolute/runtime-state init /absolute/handoff.json
python3.12 -m master_agent_runtime --state /absolute/runtime-state status PROJECT_ID
python3.12 -m master_agent_runtime --state /absolute/runtime-state health PROJECT_ID
python3.12 -m master_agent_runtime --state /absolute/runtime-state run PROJECT_ID
python3.12 -m master_agent_runtime --state /absolute/runtime-state stop PROJECT_ID
python3.12 -m master_agent_runtime --state /absolute/runtime-state reconcile PROJECT_ID
```

State must be outside the input project and ambient `/tmp` or `/var/tmp` trees. `init` and `status` perform no model calls. `run` inspects existing CLI runtimes and selects one whose catalog supports the configured model; it never substitutes another model or installs software. Use `--codex` to require an exact executable. It uses the existing login and scoped profiles and returns an integration artifact without editing the input checkout. Each activation resumes the same conversation in a fresh coherent project view: only its admitted module paths and private `.tmp` are writable; other source, oracle and dependency files stay readonly. A project lease rejects duplicate controllers. `stop` requests interruption; settlement requires observed exit/fencing. `reconcile` reads persisted acknowledged turns without new model work; unacknowledged starts retain their reservation and cannot be blindly retried.

**Validation status:** the native startup and temporary-path defects are corrected by admitting required launcher traversal reads and final native deny-glob rules, with no global setting changes or unsandboxed fallback. Local engineering actors disable apps, plugins, hooks, browser/computer use, native subagents and background goals until those routes are admitted separately. ### Runtime policy, continuation and Claude Code owners

These changes target the stalls seen in the pilots: held operations with no exit, a batch scheduler that idled the Master, unactionable rejections and missing cost detail. They are verified offline with synthetic actors and recorded fixtures; no live model run has exercised them yet.

A handoff may carry an optional `runtime_policy` object. `init` validates it strictly and stores it beside the contract, so it never changes the contract fingerprint. The `policy` operator command revises it later.

| Field | Default | Effect |
| --- | --- | --- |
| `owner_turn_timeout_seconds`, `master_turn_timeout_seconds` | contract timeout | Per-kind turn deadline, enforced by the controller |
| `interrupt_grace_seconds` | 60 | Wait after an interrupt before the owned process is closed |
| `max_continuations` | 2 | Continuations of a stopped owner turn before the module blocks |
| `max_transient_retries`, `transient_backoff_seconds` | 3, 30 | Bounded retry with exponential backoff for refused dispatches, unavailable reviews and admission turns |
| `admission_review` | true | When false, the host records a policy approval instead of a Master admission turn |
| `structured_review` | true | Rejections cite an admitted obligation with evidence; advisories never block or consume a revision |
| `fail_fast_failed_checks` | false | When true, failed admitted checks return to the owner without a Master turn |
| `provider`, `master`, `modules` | `codex` | Provider (`codex` or `claude`), model and effort per actor |
| `prices` | none | USD per million tokens per model (`input`, `cached_input`, `output`, optional `cache_write`) for estimates |
| `preflight` | false (`init`: true) | Host-only checks before any agent session: check executables, creatable paths and each check's result on the unchanged project |
| `final_acceptance` | `master` (`init`: `user`) | `user` stops a passing integration for your acceptance instead of accepting it |
| `module_review` | `always` (`init`: `checks_only`) | `checks_only` accepts a module on its admitted checks without a Master review turn and returns failing checks directly |
| `review_modules` | none | Modules that keep their Master review under `checks_only` |
| `max_decisions` | 3 | Owner questions per module the Master answers before further questions go to you |
| `master_token_budget` | none | Master tokens after which reviews fall back to checks, questions go to you and you accept the integration |
| `parallel_dependents` | `off` (`init`: `contract`) | `contract` starts an owner before its providers are accepted when an interface contract covers the dependency; the host rebases its sealed work onto the accepted code |
| `planning`, `max_obligations` | false (`init`: true), 30 | One Master planning turn before owners start: checkable obligations per module, and contracts for dependencies that have none |
| `master_probes`, `max_probes` | false (`init`: true), 8 | Executable probes that the host seals, confirms and re-runs on every later version and on the integrated project |
| `probe_author` | `master` (`init`: `verifier`) | `verifier`: an independent readonly session per module writes the probes against each accepted version's code, without the plan, and the Master rules on every confirmed failure before its owner sees it |
| `probe_timing`, `max_probe_rounds` | `accepted`, 1 | `accepted`: white-box probe turns per module after acceptance, up to `max_probe_rounds`. `draft` (Master only): the Master writes each module's probes black-box while its owner works, and they run on every submission |

**Stopped turns continue.** A deadline, budget stop, native failure, lost transport or missing receipt interrupts the turn and waits for the owned process to exit. The host then checkpoints the owner's files and sends a continuation to the same owner and context. The module blocks only after `max_continuations`, and a budget stop does not consume one. Without an observed exit the operation stays held for `reconcile`.

**Scheduling is event-driven.** One Master lane takes evidence recovery first, then reviews in submission order, then integration. Each verifier works in its own lane beside it. Owners fill `max_parallel` slots by how many modules depend on them, directly or indirectly. A blocked or failed module stops only its dependents.

**Admission is never implied.** A refused, stopped or malformed admission turn is retried within the bound, and no module work starts before an approval. `reconcile` records the verdict of an admission turn that already completed instead of asking again. A store without a verdict event counts as admitted only when the Master has already reviewed work.

**Operator commands** are journaled with a required reason and refused while a controller holds the project:

```bash
python3.12 -m master_agent_runtime --state /absolute/runtime-state resolve PROJECT_ID --operation OPERATION --outcome failed --rearm --authorization 'reason'
python3.12 -m master_agent_runtime --state /absolute/runtime-state rearm PROJECT_ID --module KEY --rounds 1 --authorization 'reason'
python3.12 -m master_agent_runtime --state /absolute/runtime-state admission PROJECT_ID --decision rerun --authorization 'reason'
python3.12 -m master_agent_runtime --state /absolute/runtime-state budget PROJECT_ID --tokens 8000000 --authorization 'reason'
python3.12 -m master_agent_runtime --state /absolute/runtime-state policy PROJECT_ID --set '{"max_continuations": 3}' --authorization 'reason'
```

`resolve` closes an operation nobody can confirm without inferring a submission. `rearm` gives a blocked module more attempts with the same owner and context. Incurred usage is never refunded. `health` names the resolve, rearm, admission, answer or accept command when one applies.

**Accounting** keeps the provider's token breakdown: input, cached input, cache writes, output and reasoning. It adds a cost estimate from the provider or the `prices` table and counts unpriced tokens separately. Each actor records its CLI version and effective configuration, and each turn trace records context compactions. History reads fall back to `thread/turns/list` and `thread/items/list` when `thread/read` lacks full turns.

**Claude Code owners** use `"provider": "claude"`, and `run` and `reconcile` accept `--claude` for an exact executable (Claude Code 2.1.263 or later). Each turn is one non-interactive `claude -p` process on a host-chosen session id that later turns resume. The flags give it an explicit tool list with no subagents, web or MCP, and prompts are denied instead of asked. Edits are allowed only on the admitted paths and private `.tmp`. Bash is allowed explicitly and always runs in the OS sandbox with network off. Its writes reach only the admitted paths and `.tmp`, and the kernel denies reads of the home folder, credential folders and control state. Only the workspace, the Master's public view, admitted interpreters and the CLI's own snapshot folders are re-opened. Unlike the Codex profile, world-readable files in the shared temp roots stay readable, because the CLI keeps its sandboxed temp directory there. Keep runtime state under the home folder so other projects' actors cannot read it. The process starts from a minimal environment, so a launching agent session's identity, messaging channel, proxies and API routing never reach it. `MASTER_AGENT_CLAUDE_ENV` names extra variables to forward, such as API-key authentication; session variables stay blocked. Claude Code reports permission mode `default` while its subprocess credential scrub is on, and the init check accepts exactly that mode, plugins built into the CLI and nothing else. The host writes the stream to `native-traces/` and uses it for command evidence, recovery and the per-run usage the result message reports. Claude Code checks structured output after the model answers and retries the whole turn when a required field is missing, so for Claude actors the fields the host already treats as optional stay optional: review advisories and previous issues, and an owner's question fields when it is not asking. Codex constrains generation to the schema and keeps every field required.

The standalone CLI must be logged in; check with `claude auth status`. File tools are enforced by Claude Code's permission rules, not by the OS sandbox, and validators still run through the Codex CLI. On 2026-10-09, with Claude Code 2.1.295 and Haiku 5.5, a live boundary probe confirmed the denials. Smoke projects and the historical atomic-publication task were then accepted end to end through this adapter.

### Operator mode: the Master runs the team, you check the result

`init` admits new projects in operator mode unless their `runtime_policy` says otherwise:
- a host preflight replaces the Master's admission turn;
- the Master plans before owners start;
- owners of dependent modules work in parallel against interface contracts;
- admitted checks accept modules, and an independent verifier probes each accepted module's code;
- you are the final checker.

Each owner still writes only its own module.

**Owners ask, the Master answers.** An owner blocked by a decision outside its module returns `needs_decision` with a question, options and its recommendation. Its files are checkpointed. The Master answers within the brief, and the owner resumes the same session with the answer. The Master escalates questions that belong to you: scope, objective or acceptance criteria, external effects, spending beyond the envelope, or an open product choice. Escalated questions, questions past `max_decisions` and questions the Master cannot answer wait for you while other modules continue. `status` lists them under `pending_questions`, and `health` names the command. An owner that returns `blocked` now keeps its files for the next attempt. When settling a question needs another module's code to change, the Master's answer lists that change and the host delivers it to that module's owner:
- an accepted module, or one waiting for its inputs, is reopened with the change as a correction;
- an idle owner reads it on its next turn;
- an owner at work, or a module with a review or rebase in flight, gets it once that ends.

Integration waits for every routed change, and the report lists them.

**You accept the integration.** When every module is accepted and the integration checks and the Master's whole-project review pass, the run ends in `awaiting_acceptance`. Nothing is applied to your project. A report at `<state>/projects/<id>/reports/` lists the integrated files, checks, modules, answered questions and usage. `accept` records your acceptance. `reject` returns the work with feedback: to named modules and their dependents with `--module`, or, without it, the Master decides which owners must change their files on the next run.

**Interface contracts.** A handoff may list `interfaces`: `name`, owning module, consuming modules and the contract text. Owners see the contracts they provide and consume, and reviews cite them. A consumer need not depend on the provider, so both can be built in parallel against the contract and the integration checks prove the composition.

**Dependent modules in parallel.** Under `parallel_dependents: contract`, a module that depends on another starts at once when an interface contract covers that dependency.
- Its view keeps the provider's original files, and the contract tells it what to code against.
- If it finishes before the provider is accepted, its files are sealed and the module waits in `awaiting_inputs`.
- When the provider is accepted, the host re-runs the dependent's checks on the sealed files against the accepted code, with no Master turn, and sends the result to review. A failure goes back to the owner with the real output, and the provider's code is now in its view.
- If an accepted provider is later sent back, its contract-built dependents keep their work and are rebased again rather than redone.

**The Master plans first.** Under `planning`, one Master turn before any owner starts expands the requirements into checkable obligations: one module, a verbatim quote of the requirement, a concrete case and the expected result.
- The host refuses obligations that do not quote the admitted objective or module objective. The Master expands scope; it cannot add any.
- Each owner gets its obligations and must name each one in its owner tests (`test_O3_...`). A host check returns a submission whose tests omit an assigned id.
- For dependencies without a contract, the plan also drafts the contract, so those owners can work in parallel too.
- A plan refused twice is recorded as unavailable, and the run continues without it.

**Independent verifiers probe every module.** Under `master_probes`, executable probes (Python scripts returned in a turn's structured output) check each module. With `probe_author: verifier`, the operator default, the Master assigns each module a verifier.
- **Who.** A verifier is a readonly actor with its own session. It did not plan, write or review the module, and it never sees the plan's obligations. It reads the accepted version's code and the owner's tests, and probes the requirements: each entry point crossed with missing, empty, foreign, partial, corrupt, concurrently changed and crashed state, every storage mode and leftover file, and every lifecycle point.
- **Why independent.** In live runs of increment 2b, the owner tests, the probes the Master drafted from its plan, and the Master's review primed by that plan all checked the same planned cases. The 48 drafted probes caught none of the hidden defects, and every defect that survived was a case the plan had never listed.
- **In parallel.** Verifiers run in their own lane, up to `max_parallel` at once, while owners build and the Master works. Their usage is reported as `verifiers` in `status`.
- **The Master rules.** A confirmed failure first goes to the Master, who upholds it when a requirement demands the behaviour, or dismisses it with a reason. Upheld failures go back to the owner with the behaviour and the expected and observed results, but not the probe code. Dismissed probes are retired and listed in your report. Without a usable ruling, every failure stands.
- **Routing.** When the fix for an upheld failure belongs in a module the verified one depends on, the Master names that module. The host sends the failure to that module's owner, and the probe then runs at integration, where a failure names that module, instead of failing every version of a module that cannot fix it.
- **Sealing and running.** The host seals the probes where no owner can read them and runs them in the validator sandbox against the module's composed view. A failure counts only when two of three runs confirm it and the probe printed its `EXPECTED:` and `OBSERVED:` lines; inconclusive probes never block.
- **All sealed probes.** They re-run on every later version and on the integrated project, where a failure names the module that must change.
- **What waits.** Dependents without a contract wait for their provider's probes and ruling, and integration waits for all of them. A failed verification job is journaled and never halts a module.
- **The Master as author.** With `probe_author: master`, the Master writes the probes instead: white-box after acceptance or, with `probe_timing: draft`, black-box while the owner works, so they gate each submission. Its probes skip the ruling.
- **Report.** It lists the plan, the drafted contracts, each probe's outcome on the accepted versions and every dismissed probe with the Master's reason.

**Your private acceptance checks.** A handoff may name an `acceptance_directory` outside the project and `acceptance_checks`, each with a `name`, `argv`, optional `timeout_seconds` and `description`. `{acceptance}` in `argv` expands to a sealed copy of that directory. No agent can read the checks, their logs or the report. The checks run against the integrated project after the Master's approval, their results go only to your report, and any failure stops the integration for your acceptance even under `final_acceptance: master`.

```bash
python3.12 -m master_agent_runtime --state /absolute/runtime-state answer PROJECT_ID --module KEY --text 'answer' --authorization 'reason'
python3.12 -m master_agent_runtime --state /absolute/runtime-state accept PROJECT_ID --authorization 'reason'
python3.12 -m master_agent_runtime --state /absolute/runtime-state reject PROJECT_ID --feedback 'what is wrong' --module KEY --authorization 'reason'
```

Offline verification on macOS with Python 3.12 and 3.14 passes 244 runtime cases, including 30 for operator mode, 24 for parallel dependents, planning and probes, and 14 for independent verifiers and routing, and 20 owner-suite cases. Live Codex checks on 2026-10-09 with CLI 0.162.0-alpha.17.2 and `gpt-6-luna` covered both a smoke project and a kill test. The smoke project was accepted after one journaled rearm; the first attempt exposed that exact write grants could not create a missing parent directory, so the host now creates parents of admitted paths. ## Core Model

The Master Agent is a control-plane role. It may update project ledgers, packets, plans, state documents, and policy packs, but it must not edit production code.

Implementation work is delegated to bounded sub-agents through explicit work orders. Strategy, coding, review, policy, learning, and custom-role agents return structured packets that the Master Agent accepts, rejects, or escalates.

Conversation is not treated as durable state. Accepted decisions and current project status must be written into the project state pack.

## Runtime Notes

- The local file provider is for offline testing and state simulation.
- `provider=codex` is the provider-command automation path. It requires `--provider-command` or `MASTER_AGENT_SESSION_PROVIDER`.
- `scripts/file_session_provider.py` is a reusable reference implementation of the provider-command JSON contract.
- `provider=codex-app` is the Codex desktop tool-mediated path. Use Codex thread tools for create/send/read/archive, then record evidence with `session-confirm-create`, `session-confirm-send`, `session-confirm-read`, and `session-confirm-archive`.
- Worktree control is also evidence-based. Use `worktree-plan`, `worktree-confirm-create`, `worktree-assign-session`, `worktree-reconcile`, `worktree-close`, and `worktree-confirm-close` so sub-agents work in isolated Worktrees instead of mutating the user's foreground checkout or remote branches.
- Run `validate-worktreeinclude` before relying on ignored local files in Codex-managed Worktrees. `.worktreeinclude` must list only intentionally ignored local setup files; tracked files, broad patterns, repository escapes, and symlinks are release blockers.
- `codex-round-log` / `change-round-logger` integration is optional and local. Use `round-log-status` to inspect repo-local snapshot health, `record-round-log-evidence` to bind a snapshot manifest to an agent receipt, `require-round-log-evidence` before accepting receipts that demand snapshot evidence, and `round-log-export` only when readable review evidence is needed. Round-log evidence complements Git status; Git remains the boundary-enforcement source.
- Repair-log document memory is repo-local. Use `repair-log-init` to create `docs/repair-execution-log/`, `repair-log-status` to inspect the current row, `require-current-repair-row` before launching or accepting work that depends on prior attempts, `record-task` for bounded non-loop outcomes, `open-repair-cycle` for repeated failure classes, and `record-repair-attempt` for each repair-cycle hypothesis. Repair records sequence work; they do not create root authorization, do not activate guard state, and do not replace the stable execution-log lineage of objective, original target error, and controlling plan/spec.
- Work orders must include `Guard Mode`. Ordinary bounded work should set `Guard activation required: no`, `Activation source: none`, `Guard state mutation allowed: no`, and `Missing activation status: loop_guard_not_required`. Do not create guard manifests, budgets, successors, disarm ceremonies, or guard-owned gates for those tasks.
- Explicit guarded work requires a current `/goal`, explicit autonomous/guarded/repeated-repair request, or a user-approved plan that names that method. `guard-obligation.md` must bind that activation source, use `already_armed` for the same manifest, reserve `active_guard_exists` for a distinct conflicting loop, and include only gates required by the user request, current goal, or approved plan.
- `accept-strategy` validates Strategy packets before they become current plan state. Coding, Review, and Policy Review registration/session launch require the current plan to carry that validation evidence.
- Use `strategy-packet-lint` for preflight diagnostics and `require-strategy-packet-before-work` as an explicit gate before issuing sub-agent work from an accepted Strategy packet.
- Use `governance-lint` before launching from a context packet, work order, receipt, review verdict, policy verdict, obstacle-recovery packet, or acceptance-gate packet.
- Use `guard-obligation.md` and `governance-lint --packet-type guard-obligation` when a task uses an implementation guard or a validation-only acceptance obligation.
- Use `record-governance-status` for recoverable guard states such as `loop_guard_not_required`, `manifest_correction_required`, `authorization_invalid`, `evidence_required`, `in_root_transition_required`, `external_mutation_domain_identified`, and `infrastructure_retry_ready`.
- Use `record-acceptance-gate` to record ordered maturity evidence. Higher gates cannot pass until all lower gates for the same scope have passed.
- Use `record-authority-required` only when an observed production mutation is outside the root authorization envelope.
- Use `request-rotation`, `validate-predecessor-state`, and `rotate-session` to replace overloaded agents. Normal rotation requires a validated predecessor-state packet; emergency rotation requires `--emergency-without-predecessor-state`.
- Use `enforce-master-boundary` before completing Master-led work, and `assess-parallelism` before running multiple sub-agents.
- Use `record-learning-correction`, `learning-cycle-start`, `learning-proposal-lint`, `accept-learning-proposal`, and `record-learning-effectiveness` to convert repeated corrections into reviewed behavior updates.
- Long-running supervision should be launched through the operating system scheduler or service wrapper appropriate for the deployment environment.
- Custom roles must have explicit approval evidence, scope, positive token budget, heartbeat cap, and deactivation conditions before activation.

Run the core checks from the repository root:

```bash
python -m unittest discover -s tests -v
python -m unittest discover -s pilots -p 'owned_*_test.py' -v
python -m py_compile scripts/bootstrap_project_state.py scripts/file_session_provider.py scripts/validate_state_pack.py scripts/master_agent_tool.py scripts/state_io.py scripts/release_validate.py scripts/soak_validate.py tests/test_master_agent_system.py
python scripts/validate_state_pack.py assets/templates
python scripts/soak_validate.py --quick
python scripts/master_agent_tool.py validate-worktreeinclude --state-dir <project-root>/docs/master-agent --project-root <project-root>
python scripts/master_agent_tool.py repair-log-status --state-dir <project-root>/docs/master-agent --project-root <project-root>
```

`tests/` is the regression suite for the legacy tool and the runtime package; the release gate runs all of it. `pilots/` keeps the frozen files of two completed runtime pilots byte-for-byte, and the second command reruns the tests their module owners wrote. See `pilots/README.md`.

Validate the skill metadata with Codex's skill validator:

```bash
python <path-to-skill-creator>/scripts/quick_validate.py <path-to-this-skill>
```

Run the release gate:

```bash
python scripts/release_validate.py --quick-validate <path-to-skill-creator>/scripts/quick_validate.py --installed-skill-dir <installed-master-agent-system>
```

`release_validate.py` runs the quick soak by default. It skips `plugin-eval` when unavailable, or treats it as a release blocker when `--require-plugin-eval` is supplied.

The GitHub Actions source example is `assets/examples/release-validate.yml`. It prepares the legacy validator and PyYAML on an isolated macOS runner, then runs the full release gate and the separate owner acceptance suite with Python 3.12 and 3.14. Copy it to `.github/workflows/release-validate.yml` in a deployment that elects to activate CI. This repository retains its existing `.github/` exclusion; the example is included in source releases without activating a workflow.

The tests are not required for minimal runtime installation, but they are recommended for source releases because they protect the safety-critical behavior of the skill pack.
